# B08 审核记录：API 层（REST + WebSocket + 定时调度）

状态：✅ 已通过 · 日期：2026-10-18（同日真机验证并审核通过）

## 范围（开工时和用户确认）
- **核心路由**：设备、模块列表 / 配置 schema / 保存的配置、任务启停和状态、统计、日志、调度。**模板采集推迟到 B09**，和 GUI 的框选页一起做。
- **WebSocket**：`/ws` 是控制 + 事件频道（JSON），`/ws/frames` 是帧频道（二进制 JPEG），两者分开。
- **定时调度**：三种触发方式（间隔 / 每天北京时间固定时刻 / 由模块给出下次时间）。
  - 到点时有任务在跑：**排队，带等待上限**（用户选）。每条计划也可以改成跳过。
- **daily**（用户意见）：模块提供计时供 GUI 显示倒计时；每日收菜由用户选择单次执行还是持续收菜。
  - 单次 = `POST /tasks`；
  - 持续 = 一条 `module` 触发的计划：重置后跑一次，精灵之森到时间再跑。
- **监听和鉴权**：默认 `127.0.0.1:47800`，**随机 token + Host 校验**（用户选），开发时可以 `--no-auth`。

### 路由（前缀 `/api`，详见 architecture.md）
- **基础**：`health`（不需要 token）、`status`、`logs`
- **设备**：
  - `GET /device`、`POST /device/connect`、`POST /device/disconnect`、`GET /device/instances`
  - 只读：`GET /device/screenshot`、`GET /scene`
- **模块**：
  - `GET /modules`、`GET /modules/{id}`（含 `config_schema`）
  - `GET/PUT /modules/{id}/config`、`GET /modules/{id}/stats`、`GET /modules/{id}/timers`
  - 模块子路由挂在 `/api/modules/{id}/...`
- **任务**：`POST /tasks` → 202（409 busy / 422 invalid_config / 503 no_device）、`GET /tasks/current`、`POST /tasks/stop`、`GET /tasks/history`
- **助手**：`GET /assistants`、`POST /assistants/{id}`、`DELETE /assistants/{id}`
- **调度**：`GET/POST /schedules`、`GET/PATCH/DELETE /schedules/{id}`、`POST /schedules/{id}/run`、`PUT /scheduler {paused}`

### WebSocket 协议
- `/ws?token=`：
  - 连上后先收到 `hello`（同 `/api/status`）。
  - 请求 `{"id","op",...}`，每个都有 `reply`。操作有 `ping` / `status` / `subscribe`（topics、log_level）/ `unsubscribe` / `start_task` / `stop_task` / `run_schedule` / `pause_scheduler` / `resume_scheduler`。
  - 事件 `{"type":"event","topic","time","data"}`。默认什么都不订阅，`*` 表示除帧以外全部。
  - 每个客户端的事件队列 1000 条，满了丢最旧的；回复不丢。
- `/ws/frames?token=&fps&scale&quality`：
  - 二进制 JPEG：有任务时转发任务截图，空闲时自己截图（只读）；
  - 设备没连上时每秒发一条 `{"type":"status","connected":false}`。

### 调度的已知需求怎么配
- `repeat_battle` 只开托管：`{"module":"repeat_battle","trigger":{"type":"interval","minutes":30},"config":{..., "manual":false, "auto_battle":true, "dry_run":false}}`
- `daily` 持续收菜：`{"module":"daily","trigger":{"type":"module","min_interval_minutes":10},"config":{..., "dry_run":false}}`
  - `next_due`：本游戏日还没成功跑过就马上跑，否则取「下一次重置（北京时间 3 点）」和 `forest_next` 中较早的；
  - `forest_next` 早于上次成功的不作数；关了精灵之森就不看它。
- `daily` 单次收菜：`POST /tasks {"module":"daily"}`（用保存的配置）。
- 安全：计划的 config 是完整快照，调度器不改 `dry_run`。模块默认都是 dry-run，所以计划要实跑，必须在计划里明确写 `dry_run:false`。

- **验证中发现并修复的问题**：
  - **现象**：CTRL_BREAK 关服务时，uvicorn 已经正常关闭（急停、关设备都执行了，日志里有 `Application shutdown complete`），但 **api.json 没删掉**。
  - **原因**：uvicorn 关闭后会重新抛出收到的信号，Windows 上 SIGBREAK 的默认处理是直接结束进程，`serve` 里 `server.run()` 之后的清理没执行。
  - **修复**：`create_app(..., on_shutdown=[...])`，在 lifespan 关闭的最后一步删 api.json。
  - **复测**：不连设备、独立数据目录，`api.json 已删除: True`。退出码仍是 3，这是 SIGBREAK 默认的退出码，不影响清理。
  - 残留的 api.json 对应的进程已经结束，已手动删除。

## 已知问题 / 说明
1. **api.json 可能残留**：服务被强制结束时 api.json 会留着，例如 Windows 的 `TerminateProcess`（任务管理器、`proc.kill()`，Tauri 结束 sidecar 大概也是这样）。Ctrl+C / CTRL_BREAK 会正常删除。读取方要用 `pid` 或 `GET /api/health` 确认服务还在。
2. **时间格式不统一**：任务记录和日志用 unix 秒（沿用 runtime 的 `TaskResult` / `LogBridge`），计划和计时用带时区的 ISO 字符串（UTC）。B09 前端需要两种都处理；要统一的话可以在 B09 前定。
3. `--paused` 会写进 `schedules.json`：下次启动不带 `--paused` 也还是暂停，要 `PUT /scheduler {"paused": false}` 恢复。
4. `daily` 计划某一项失败（任务记为 failed）时，不算「本游戏日成功跑过」：按最短间隔 × 2 的幂重试，连续 3 次就停用。这样能避免一直重试，但也意味着游戏不在大厅时持续收菜会被停用，需要用户手动重新启用。
5. 每日固定时刻的计划在排队超时后跳过，要等到第二天。
6. 调度器每秒重新计算所有计划的下次时间：`module` 触发每次都会读一次 `ledger.json`，开销可以忽略。
7. 测试有一条 Starlette 的弃用警告：TestClient 建议改用 `httpx2`。只影响测试，没处理。
8. 设备掉线（例如 MuMu 被关）后 Engine 仍认为已连接；截图 / 场景接口返回 503 `device_error`，需要 `disconnect` 后再 `connect`。任务里的设备错误照旧按任务失败处理。B09 可以按需加心跳自动重连。
9. 模块子路由在服务启动时挂载一次，之后新增的模块（entry-point）要重启服务才生效。
