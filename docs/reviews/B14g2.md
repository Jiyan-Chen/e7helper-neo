## 起因
接 B14g1。0.4.0-beta.1 的 RTA 助手里，准备选「挑战者及以下 vs 战神」时推荐的预期只有 3.1%（「传说 vs 传说」同一组 63.1%）：快照里的段位是赛后的，旧模型学成了「段位高的一定赢」。B14g1 训好了不看段位、带「先手方先动 / 后手方先动 / 不知道」三个胜率头的新模型（暂存在 `F:\e7helper-data\rta\bundles\b14g1\`），本块把它接进搜索、接口、命令行和页面，换进随包。用户原则：段位只影响「谁先动」，胜率按英雄 BP 算，再按先动概率混合。

## 方案（按 B14g1 审核记录末尾的设计草案做，没有拆子块）
- 换模型：`b14g1\` → `engine/assets/data/rta/`（主模型 + `second/`）；旧的 B14h 随包模型备份到 `F:\e7helper-data\rta\bundles\b14h\`（计时对比用）。`rta priors` 重新生成，加上每一手的选取次数（`slots`）。
- 搜索：`_Net.forward` 一次前向取三个头，每行按自己的阵容算先动概率（first = 双方段位 + 我方英雄池速度，ref = 一般玩家），`model.effective_first` → 混合。推荐、最坏、对手回应、后禁矩阵、`opponent.win`、预禁都走这里，一处改全改；没有速度表时用「不知道」的头。
- 显示：每个值都带着「我方先动时 / 后动时」两种（同样的回应、权重、修正），鼠标提示给两种胜率（用户意见）；显示的先动概率只按双方已选的英雄（审核第 1、2 轮）。
- 用时：先动概率加了快速档和缓存（见「用时」）。

## 搜索里怎么混合（`core/rta/search.py`）
- `Advisor` 带速度表（`search.load()` 读随包 `speed.json`）和一个 `FirstCalc`（占位按 `priors.json` 的整体 / 每一手选取次数）。没有速度表时用「不知道」的头（`info().mix` = `unknown`），推荐照常。
- 每次搜索建一个 `_FirstCtx`：双方段位、我方英雄池里填的速度（对方的不知道）。`_Net.forward` 每次前向取三个头，同一批局面按各自阵容算先动概率（`speed.ids_first_probs`）：
  - first = 按双方段位 + 我方速度，ref = 同一阵容按一般玩家（不知道段位、没填速度），交给 `model.effective_first`；
  - 没选满的几手按「这一手常被选的英雄」补；一方 5 名都在、还没后禁的行对 16 种被禁平均（后禁矩阵那 16 行每行按自己的被禁算）；同一阵容（不管顺序）只算一次；
  - 局面里模型没见过的英雄（UNK）按它自己的编号查速度表。
- 推荐、最坏、对手回应、后禁矩阵、`opponent.win`、预禁（还没选人：全靠两方段位的占位）都是混合后的值；第二个模型用同一份 first / ref、自己的三个头。
- 我方速度进了推荐的缓存键（以前速度只影响显示，不在键里）。
- `Advisor.win(states)`：和搜索同一口径的胜率，`rta sim` 的胜率曲线、`rta audit` 的自对弈 / 跟着推荐改用它。

## 显示：两种胜率和配套的先动概率
- 每个值都带着「我方先动时 / 后动时」两种：叶子是模型的两个头，往上按同样的回应权重、同样的高估修正加权；后禁博弈的值 = ½ 最坏（取最坏那一格的两种）+ ½ 预期（按对方后禁率加权）。
- 输出（接口 / `--json`）：推荐、对方的每种选法、`opponent`、后禁矩阵每格（`ban.win_first` / `ban.win_second` / `ban.first`）、每行（`row_stats`）、结束时的结果都有 `win_first` / `win_second` 和 `first`（我方先动的概率）。
- `first`（审核第 1、2 轮改；最初提交时是从主数字反解、把对方回应合进去的 π）：选秀中只按双方已经选出的英雄用速度表算（推荐 = 加上这一组、对方的每种选法 = 加上对方这一手、`opponent` = 当前已选的；一方还没有英雄时 null）；后禁每格 = 4 打 4 混合用的 π（π × 先动时 + (1 − π) × 后动时 正好 = 这一格）、每行 = 4 格按对方后禁率平均。顶层 `first` = 当前局面的 `{mine, partial}`，`speed.annotate` 只再加速度表读数 `heroes`（命令行「谁最可能先动」用）。
- 前端：推荐卡的预期 / 最坏、对方的每种选法、后禁矩阵每格和每行的「预期」、信息条、结果页的胜率，鼠标提示是「我方先动时 x%，后动时 y%」（`splitTip`）；信息条的先动概率用引擎给的配套值（`pickHeadline` / `banHeadline`，旧结果没有时照旧）。
- 命令行：`rta advise` 推荐表加「先动时 / 后动时」一列、后禁矩阵每格下面「先动 x% · a/b」、对方回合打印「我方的读数」和两种；`rta sim` 推荐和胜率曲线带上英雄池速度、用混合胜率。

## 用时
接上后第一次跑复现用例 4.7–5.0 秒、多数被截断。剖析：先动概率占约 2 秒（8 万行，一半是赫尔赛蒂的限速分档），主要花在 `team_log` 的 [B, m, K] 大数组上。改了三处：
1. `FirstCalc` 可以设网格步长、限速分档数、精度，搜索用快速档 `speed.FAST`（每档 4 速、4 档、float32）；评估（`rta eval`、`tools/rta_holdout.py`）照旧用默认，B14g1 的指标不受影响。随机 6000 组阵容和默认比：差中位 0.02、p95 0.07、最多 0.11 个百分点；快 7 倍（0.197 → 0.028 秒）。限速 4 档和 8 档几乎一样：有赫尔赛蒂的阵容几乎总是她那一方先动（除非对方有开局加行动条的）。
2. `team_log` 不再乘掩码（先全加、再减掉空位那一行），积分预分配数组。
3. `FirstCalc.tables` 按编号 / 段位 / 速度 / 限速缓存（只读数组；限速英雄自己那一行改成在求和后替换，不再改表）。

## 已知问题 / 后续
1. **advise 慢了约 0.4 秒**（audit p95 3.60 → 4.00 秒，同机交替计时 3.77 → 4.56 秒），在 6 秒门槛内。要再快：网格再粗一点（每档 5 速差 p95 0.13 个点），或者跨批缓存同一阵容的先动概率。
2. **显示的先动概率和混合用的不是同一个数**（审核第 1、2 轮）：页面上（选秀中）只按已选英雄、用速度表；算胜率时按补全的阵容、再加模型隐含的先动概率（B14g1 的 `effective_first`）。所以推荐卡上 先动 × 先动时 + 后动 × 后动时 不等于预期，选秀早期两者可能差很多（复现用例当前局面：显示 5.5%，算胜率用 52.1%）。后禁矩阵每格两者一样。
3. 先动概率只用我方英雄池里填的速度，对方的一律按段位的速度分布；`POST /api/rta/first`（单独的先动试算，页面没用）还是速度表的蒙特卡洛，没有混合。
4. 预禁推荐只是数值改成混合，没加两种胜率（还没选人，先动 / 后动差很小）。
5. 高估修正常数没改（1.5%，混合后最接近 1.25%，误差差 0.0008）。
6. B14g1 的已知问题照旧：段位对先动概率的影响只来自官方按段位的速度直方图，快照里的赛后段位验证不了；选秀中间的占位还是偏向已选人数多的一方（有模型隐含的先动概率兜着）。

## 请用户重点看
- 页面上推荐卡、后禁矩阵每格、信息条的鼠标提示：「我方先动时 x%，后动时 y%」这样写是否合适、放的位置是否够（现在是推荐卡右边的预期 / 最坏 / 先动那一块、矩阵每格、每行预期、信息条胜率、结果页胜率、对方每种选法）。
- 显示的先动概率只按已选英雄（第 1、2 轮意见），和算胜率用的（补全 + 模型）不是同一个数，这样是否可以（上面第 2 条）。
- 用时多 0.4 秒能不能接受。
