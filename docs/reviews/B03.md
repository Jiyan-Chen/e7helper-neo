### 内置场景与弹窗
| 名称 | 判定 | 关闭方式 |
|---|---|---|
| 场景 `lobby` | `lobby/shop` + `lobby/secret_shop` | |
| 场景 `secret_shop` / `shop` / `arena` / `sanctuary` | 对应的 `title/*` | |
| 弹窗 `network` | `popup/network_error` + `popup/network_retry` | 点「点击重试」 |
| 弹窗 `notice` | `popup/notice`（通知中心面板，不压暗背景） | 返回键 |
| 弹窗 `confirm` | `dialog/cancel` + `dialog/confirm` | **点取消** |
| `obscured`（兜底） | 场景锚点或 `back` 探针命中处的亮度不到模板的 0.6 倍 | 返回键 |

## 验证命令（在 `engine/` 下）
```
python -m uv run pytest -q
E7_DEVICE_TESTS=1 python -m uv run pytest -q -m device     # 游戏停在大厅、没有弹窗时
python -m uv run e7helper scene -f tests/fixtures/sanctuary_help.png -f tests/fixtures/lobby_network_error.png
python -m uv run e7helper scene                            # 识别当前画面
python -m uv run e7helper scene --watch                    # 手动切几个界面看输出，Ctrl+C 结束
python -m uv run e7helper run hello -c '{"screenshots": 3}'
python -m uv run e7helper run hello -t 0.001               # 超时：状态 timeout，并打印调试目录
```
如果想手动验证弹窗：在大厅按返回键调出「确定要结束游戏吗？」，然后运行 `e7helper scene --dismiss`，它应该点「取消」。

## 实测结果
- pytest：`174 passed, 7 skipped`（B01/B02 的 84 个 + B03 新增 90 个；7 个 skipped 是真机测试）。
- 真机测试：`7 passed`（B01 的 3 个 + B03 的 4 个）。最终版本连续跑 5 次全部通过。
- 导航压力测试（最终版本）：秘密商店往返 15 次，圣域、竞技场往返各 5 次，共 25 次。补点 0 次，误按返回键 0 次。
  - 进入耗时：秘密商店 2.1–2.5 秒，竞技场约 2.1 秒，圣域约 3.9 秒；返回大厅 1.5–3.0 秒（都包含等界面静止的时间）。
- 场景判定：11 张 fixtures 在 1600×900、1280×720、1920×1080 下全部正确：

  | fixture | 场景 | 弹窗 | 压暗 |
  |---|---|---|---|
  | lobby | lobby | – | |
  | lobby_exit_confirm | 未知（遮罩盖住了大厅入口） | confirm | |
  | lobby_network_error | 未知 | network | |
  | secret_shop / secret_shop_scrolled | secret_shop | – | |
  | secret_shop_refresh_confirm | secret_shop | confirm | 是 |
  | shop / arena / sanctuary | 对应场景 | – | |
  | arena_notice | arena | notice | |
  | sanctuary_help | 未知 | obscured | 是 |
- 识别耗时：每帧 17–35ms。有弹窗时更慢，因为两个对话框按钮的检索区域大，各约 15ms。
- 真机 CLI：
  - `scene`：大厅识别为 `lobby`。按返回键后识别为 `confirm`；`scene --dismiss` 点了「取消」，回到 `lobby`。
  - 网络异常弹窗出现时（实测中自然发生），`scene --dismiss` 点「点击重试」，原来的请求完成，进入了秘密商店。
  - `run hello -c '{"screenshots": 3}'`：`succeeded`，3 次都打印「场景：lobby」。
  - `run hello -t 0.001`：`timeout`，调试目录里有 `last_frame.png`、`screen.png`、`info.json`、`error.txt`、`log.txt`。
- 游戏操作全程只点了：入口（秘密商店、商店、圣域、竞技场、铃铛、「?」）、返回、取消、点击重试。没有点立即更新和购买。天空石前后都是 19,891（最后用 OCR 复核过）。

## 过程中发现的问题与决策
1. **遮罩检测改用亮度比，不用 diff**：起初用「锚点 diff > 30」判断压暗，结果圣域被误判。原因是返回键在天空背景上的 diff 本来就有 31。
   - 改为比较命中位置 98 分位灰度与模板自身的比值：正常 ≈ 1.0，压暗 0.15–0.33，阈值 0.6。
   - 这种方法与背景无关，对非白色模板也适用。
2. **`back` 的 `max_diff` 从 30 调到 45**（改动了 B02 的资源）：圣域天空背景上 diff 是 31.4，会导致找不到返回键。压暗时 ≥ 84，余量足够。B02 的 fixtures 测试仍然全部通过。
3. **界面没静止时点击无效**：进秘密商店时，0.6 秒就能认出标题，但列表还在飞入。帧间差依次为 79 → 54 → 18 → 10 → 13 → 8，1.7 秒才静止。这期间按返回键会被忽略：1.3 秒时发的返回键无效，2.1 秒及之后发的都有效（8/8）。
   - 最初只比较标题锚点的 diff 是否稳定，但标题比列表先稳定，不够用。
   - 改为比较整帧：连续截图的 160×90 灰度均差 < 5 且持续 0.5 秒。实测待机动画（大厅海浪、商店人物）≤ 3.8，过渡时 ≥ 8。
4. **大厅「秘密商店」入口的可点区域只是图标和文字上半部分**：起初在识别到的文字框内随机点击，约 1/3 无效。
   - 排查过程：
     - 和按压时长无关（40ms 6/8，120ms 5/8）；
     - 和触控通道无关（IPC 9/12，adb 8/12）；
     - 和网络无关：失败时 40 秒内画面完全不变、也没有弹窗，ping 1ms；
     - 纯客户端的「?」说明弹窗，IPC 和 adb 都是 20/20。
   - 统计点击坐标后发现：成功的 y 都 ≤ 456，失败的 y 都 ≥ 457。直接点上方图标 (70, 412) 是 8/8。
   - 处理：`TemplateMeta` 新增 `tap` 字段（可点区域，与 `box` 同时刻记录，运行时按命中偏移平移），`tap_match` / `tap_template` 自动使用；`capture` 新增 `--tap`。`lobby/secret_shop` 设为 `tap: [40, 385, 70, 62]`。
   - 另外新增导航用的 `tap_until(target, scene)` 作为保险：等目标场景，途中自动处理弹窗；停在原场景超过 `retry_after`（默认 6 秒）再补点，最多 3 次；画面已经变了就不补点。压力测试中没有触发补点。
   - 测试中途还遇到一次真实的「网络连接异常，请重新连接。/ 点击重试」，已采集为 fixture，并注册为内置弹窗 `network`（自动点重试）。重试后原请求完成，进入了秘密商店。
5. **过渡动画被误判为未知弹窗**：第一次压力测试（25 次往返）没有触发补点，但遮罩兜底按了 13 次返回键。原因是淡入淡出时画面整体变暗，看起来和弹窗遮罩一样。
   - 处理：`dismiss_popups` 关闭 `obscured` 之前先复核，要求画面压暗且静止 0.5 秒（真弹窗的背景是静止的），在动就继续等。复核后同样的压力测试是 0 次。
6. **网络重试会重发原请求**：如果原请求是「确认刷新」或「购买」，重试就会再发一次。这是任务已经决定要做的操作，所以自动重试是安全的；但 B04 计数时，应在重试后重新核对天空石和金币，而不是按点击次数计。
7. **`confirm` 弹窗一律点取消**：结束游戏、立即更新、购买的确认框都长一样。自动处理只点取消，任务自己打开的确认框要在调用 `dismiss_popups` / `wait_scene` 之前自己处理。测试用模拟器断言从未点过确认。
8. **急停不能被模块吞掉**：`TaskAborted` 继承 `BaseException`（与 KeyboardInterrupt 同理），有测试覆盖。
9. **core → modules 的依赖**：`core.runtime.runner` 引用了 `modules.base`（模块契约）。调度器需要知道契约，这是唯一的例外，已写进 architecture.md。`modules.base` 只在类型检查时引用 core.runtime，没有循环导入。
10. **Runtime 不修改全局日志级别**：失败时写入的 `log.txt` 只包含通过 logger 级别过滤的记录。CLI 设为 INFO，所以能看到 INFO 及以上；单元测试里需要显式设置级别。

## 已知问题 / 后续
- **登录后的公告 / 每日签到 / 活动推送：不做自动处理**（用户决定）。由用户自己把游戏点到大厅，再启动任务。任务开始时默认游戏已经在大厅，或在大厅能到达的界面上。这几种弹窗如果中途出现，仍然由遮罩兜底（返回键）尝试关闭；关不掉就会因 `wait_scene` 超时或卡死检测停止，并保存调试截图。
- 大厅上的未知弹窗：如果把大厅入口都盖住了，大厅又没有返回键，遮罩兜底不生效，只会报告「未知」。目前已知的大厅弹窗（结束游戏、网络异常）都已单独注册。
- 卡死检测的默认参数（画面静止 30 帧且 60 秒；同场景 120 次且 300 秒）还没在长任务里验证，B04 实跑时再调。
- 其他入口的可点区域没有逐个验证。圣域、竞技场入口按文字点，压力测试里都是一次成功；商店入口只在采集 fixture 时点过一次。以后发现点了没反应，先怀疑可点区域，用 `capture --tap` 补上。
- `tap_until` 的补点间隔（6 秒）是经验值。网络很慢时，可能在请求还没返回时补点；对导航按钮来说这是无害的。
- 大厅顶栏的布局和 B02 的 fixture 不一样了（体力、天空石的位置右移），B02 测试里的 OCR 区域只对 fixture 有效。B04 读天空石时要先用 `top/skystone` 定位，再按偏移读数字。
- 运行时只在单进程内保证互斥。B08 的 API 服务也是单进程，够用。
- 新增 fixtures 约 11MB，fixtures 总计约 16MB（按约定不用 LFS）。
- 帧事件的频率由任务截图频率决定，任务空闲时由帧泵按 0.5 秒补帧。B11 的 RTA 助手如果需要更高帧率，再调 `frame_interval`。
