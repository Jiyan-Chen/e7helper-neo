## 起因

本会话再核对了一遍（B14h 快照）：

其余是我按数据定的（下面各节有依据）：
- 胜率头分三种「谁先动」（先手方先动 / 后手方先动 / 不知道），不是把「谁先动」当输入跑两遍：一次前向就有两种胜率，搜索的推理量不翻倍；选人头不看它（选秀时还不知道谁先动）。

## 模型改动
- **去掉段位**：`TrainConfig.grades = False`，CTX 只加开战规则；ctx 数组格式不变（旧模型要用），新模型不看前两项（单元测试核对：改段位，输出完全不变）。
- **三种「谁先动」**（`TrainConfig.first = True`）：
  - Transformer 胜率头 `Linear(d → 3)`；
  - 因子分解机另加 `FirstTerm`：Δ = 每个局面一个常数 + 在场英雄各自的「先动敏感度」之和（不分哪一方），先手方先动 +Δ、后手方先动 −Δ；「不知道」是单独的头（不是两者的平均）。
  - ONNX 输出 `win_logit` [B, 17, 3]，`meta.json` `format: 2`、`first_heads`、`grades: false`，校准每个头一组（先手方先动的头只用先手方先动的对局拟合，「不知道」用全部）。
- **训练**：快照的 `first_mover`（实际谁先动）→ 每场的头编号；损失 = 每场「不知道」头的 BCE + 知道谁先动的再加那一方先动的头，一起平均。训练集 72% 的对局知道谁先动（早期对局采集时还没存开局行动条）。
- **兼容**：旧格式模型照样能读（三种情况一样）；`fit.load_run` 读旧 run（设置里没有 `grades` / `first`）按旧结构建网络；`rta train --with-grades` / `--no-first` 只做对比。随包的 B14h 模型这一块没动，搜索照常用它。

## 快速先动概率（`speed.FirstCalc`）
评估要给 17.4 万场 × 12 个局面算先动概率，B14g2 的搜索每次也要算几千个阵容，原来的蒙特卡洛（每次 4000 次抽样）太慢。
- 同一个模型按速度分布直接积分：一方最先到的时间 T = min tₕ，英雄独立 → P(T > x) = Π P(tₕ > x)，P(先手方先动) = ∫ P(T_S > x) d(−P(T_F > x))；时间按「等效速度」640 … 40 每档 2 离散，每名英雄（段位、填的速度、限速）的对数生存函数缓存。
- 和 4 万次抽样对照：随机 300 组阵容差 p95 0.4 个百分点（单元测试 40 组 ≤ 2 个点）。
- **赫尔赛蒂**（限速让英雄不再独立）：按她的速度分 8 档分别算再平均。测试期 18.2% 的对局有她，逐场算太慢（5000 场 9 秒），改成整批按档算。
- **选秀中间还没选的那几手**用「占位」补到 4 名：
  - 起初用官方直方图的合计：第 5 手平均 64%（实际先手方先动 52%），因为 RTA 里常选的多是快的；
  - 改成按 RTA 选取次数加权：62%；
  - 再按「一方第几手」分别加权（`slot_counts`，先选的多是快的、后面几手偏慢）：56.7%，第 5 手 log loss 0.627 → 0.575，其余中间几手也都更准。
- 5 名都在、还没后禁时，对 4 × 4 种被禁的情况平均（保护位不会被禁）。
- 评估 2 万场 × 12 个局面约 33 秒。

## 先动概率怎么混合（`model.effective_first`）
直接用速度表的先动概率 π 混合（π × 先手方先动时 + (1 − π) × 后手方先动时），在测试集上**比「不知道谁先动」的头还差**：n11 0.6257 vs 0.6238（只用 50/50 混合是 0.6299，知道实际谁先动是 0.6099）。逐行查（切分模型、测试期）：
- 两个头在条件上是准的：速度表说五五开（0.2–0.8）的对局里，先手方实际先动时实际胜率 62.3%、先手方先动的头 61.5%；后手方先动时实际 40.6%、后手方先动的头 40.5%。
- 问题在先动概率：在「谁先动最要紧」的对局里（两种胜率差 > 30 个点，1.8 万场），速度表预测谁先动反而不如模型从对局里学到的（log loss 0.590 vs 0.519），混合后 0.666 vs「不知道」的头 0.649。官方速度直方图混着 PvE 配装，偏偏在抢速的阵容上最不准。

改成：π = σ(logit π速度 + w · (logit q − logit π一般))
- π速度 = 速度表按双方段位 + 英雄池速度 + 开局规则算的；π一般 = 同一阵容按「不知道段位、没填速度」（一般玩家）算的（`speed.first_pair` 一次给出两个）；
- q = 模型自己隐含的先动概率：「不知道」的头 = q × 先手方先动时 + (1 − q) × 后手方先动时，由三个头反推；
- w = 差² / (差² + 0.1²)，差 = 两种胜率之差。

意思是：抢一速要紧的阵容，以模型从对局里学到的「一般玩家这一局谁先动」为底，段位 / 速度只带来速度表上的变化量（双方一般玩家时混合结果 ≈「不知道」的头）；谁先动无所谓的阵容（差小，q 反推不稳）就是速度表——这时混合结果几乎不受影响，主要为了显示的先动概率稳定。

| 测试期 n11（切分模型，17.4 万场） | 胜率 log loss | 当先动预测：log loss / 命中 |
|---|---|---|
| 50/50 混合 | 0.6299 | — |
| 直接用速度表混合 | 0.6257 | 0.2315 / 90.1% |
| 「不知道谁先动」的头 | 0.6238 | — |
| q + 段位变化量（w ≡ 1） | 0.6233 | 0.7013（差小时 q 乱跳） |
| **随包用的（τ = 0.1）** | **0.6231** | **0.2348 / 91.2%** |
| 知道实际谁先动 | 0.6099 | — |

τ 是在测试期上比的（0.05–0.1 胜率一样，0.1 先动预测更稳），所以另用两个全量模型都没见过的 11-02 核对（见下）：结论一样。

## 已知问题 / 后续
1. **随包模型还是 B14h 的**（用户选的拆分）：0.4.0-beta.1 的 3% 问题要到 B14g2 换模型 + 接搜索后才消失。
2. 混合用的先动概率和速度表不完全一样（测试期中位差 2.8 个点、90% 差 20 个点，都在抢一速要紧的阵容上）。B14g2 接界面时，显示的「先动 x%」要换成混合用的这个，否则鼠标提示里「先动时 / 后动时」两种胜率按显示的先动概率算不回主数字。
3. 段位对先动概率的影响只来自官方按段位的速度直方图，我们的数据验证不了（快照里是赛后段位，和谁先动几乎无关）。
4. 选秀中间的占位仍偏向已选人数多的一方（第 5 手平均 56.7%，实际 52%）；混合时有模型隐含的先动概率兜着，影响小。
5. τ = 0.1 是在测试期上比出来的，留出日核对过；以后重训照用，结果明显变了再看。

## B14g2 设计草案（开工时细化）
1. **换模型**：`F:\e7helper-data\rta\bundles\b14g1\` → `engine/assets/data/rta/`（主模型 + `second/`）；`rta priors` 重新生成并加上每一手的选取次数（`speed.slot_counts`，占位用）。
2. **搜索**（`search.py`）：`Advisor` 建一个 `FirstCalc`（速度表 + priors 的选取次数），每次搜索按局面的双方段位、我方英雄池速度建两份表（按段位 / 一般玩家），缓存起来；`_Net.forward` 取三个头 → 每行按阵容算 first / ref（`prob_batch`，主模型编号，UNK 用占位；5 名都在、还没后禁的行对 16 种被禁平均，后禁矩阵那 16 行正好就是这 16 种，后禁前的值取平均）→ `model.mix`。第二个模型用同一份 first / ref、自己的三个头。推荐、最坏、对手回应、后禁矩阵、`opponent.win`、预禁都走这里，一处改全改。没有速度表时用「不知道」的头。
3. **用时**：先量每批多出的时间（限速英雄的行要 8 倍），advise p95 ≤ 6 秒；不够就在 `FirstCalc.tables` 上加缓存。
4. **显示**：`annotate` 的先动概率换成混合用的（`effective_first`），推荐卡 / 后禁矩阵每格的鼠标提示给「我方先动时 / 后动时」两种胜率（后禁矩阵 4 打 4 是精确的；推荐卡取这一手之后的局面）。接口 / CLI（`rta advise` / `sim`）/ 前端跟着改。
5. `tools/rta_trust.py`（高估修正常数）改用混合的胜率重新量；`rta audit`；复现用例（预期只因先动概率小幅变动）；全量 pytest、前端测试、`rta model --check`；冻结引擎冒烟测试按需。
